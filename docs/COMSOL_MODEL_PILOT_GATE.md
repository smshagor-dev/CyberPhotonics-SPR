# Stage 10 — COMSOL Model Inspection and One-RI Live Pilot

Previous stages can preregister and execute batches with source-bound logs. Stage 10 provides a separate **pre-execution model readiness gate** so invalid geometry parameters, missing studies, absent materials/mesh or incorrect unit configuration can be detected before running an entire inverse-design verification campaign.

**Important:** A passing gate is operational readiness ONLY. Neither a live solver pilot nor hash consistency establishes correct Maxwell equations, physical fabrication, mesh/PML convergence, mode selection, real experimental measurement or journal-readiness.

## 1. Static gate — requires no COMSOL

```bash
python scripts/probe_comsol_model.py --plan outputs/research/stage7_plan --benchmark outputs/research/stage4 --model /real/validated_pcf_spr.mph --config /real/solver_settings.yaml --out outputs/research/stage10_static
```

This validates all frozen plan, original benchmark, model and config hashes. The YAML must explicitly specify study, wavelength/loss expressions, finite positive conversion factors and a physically bounded wavelength range. It refuses template filenames containing `.example.` and obvious placeholder values.

The static report is **not permission to start a full solver campaign**. It cannot detect a false `.mph` file, an expired COMSOL license, incorrect mode assignment or invalid materials.

## 2. Live structural inspection — loads COMSOL model but does NOT solve

```bash
python scripts/probe_comsol_model.py --plan outputs/research/stage7_plan --benchmark outputs/research/stage4 --model /real/validated_pcf_spr.mph --config /real/solver_settings.yaml --out outputs/research/stage10_live --live
```

This uses the licensed MPh COMSOL API to load the actual file, inspect named global parameters (`d_over_lambda`, `pitch_um`, `metal_thickness_nm`, `analyte_ri`, `channel_radius_um`), check the exact study name from config, and require at least one geometry, mesh, physics and material definition, without reported model problems. A mismatch is a blocking result. The model-saved COMSOL version and element names are reported for human inspection.

If the plan study uses COMSOL's internal tag `std1` but MPh exposes the actual study **name** instead, update the model-specific config to the proper study name and preregister a NEW frozen Stage 7 plan; never edit an already hashed plan to make an error disappear. See [MPh documentation](https://mph.readthedocs.io/en/stable/api/mph.Model.html).

## 3. Explicit real solver pilot — one center RI, no fabricated fallback

```bash
python scripts/probe_comsol_model.py --plan outputs/research/stage7_plan --benchmark outputs/research/stage4 --model /real/validated_pcf_spr.mph --config /real/solver_settings.yaml --out outputs/research/stage10_pilot --live --pilot --strict
```

Only with `--pilot --live` does this call the repository's actual COMSOL `mph` solver. It selects the **central analyte RI** of the first frozen Stage 4 request, solves that single geometry and archives wavelength/loss spectra with numerical consistency checks and SHA-256. Failure to initialize, load, solve, or extract an adequate spectrum produces a fail-closed report and strict exit 2.

The pilot is one RI point only. It cannot estimate RI sensitivity or FOM, validate the mesh, or demonstrate superiority over baselines. All outputs retain `source_authenticity_verified=false`, `physical_correctness_verified=false` and `scientific_submission_ready=false`. Preserve the genuine native COMSOL log from the pilot independently; this tool does not capture it automatically.

## Outputs and research limitations

- `COMSOL_MODEL_PILOT_READINESS.json`: SHA-bound plan/model/config sources, explicit structural checks, solver backend observed, blockers, source limitations and readiness flag.
- `pilot_single_ri_spectrum.csv`: generated ONLY if an explicit pilot was attempted and produced a parseable solver row. Its spectral values, if present, are **unqualified** and may NOT be copied directly into the paper.
- `--strict`: returns exit code 2 unless a *real* pilot successfully produces a numerically consistent spectrum. Test-injected runners are labeled `software_fixture` and **cannot** enable `ready_for_full_solver_run`.

GitHub Actions deliberately uses Stage 7's dummy `.mph` model with the example YAML for a **static rejection** regression. It never runs COMSOL; no model or spectrum generated by CI can establish physical sensor performance.

After a real pilot passes, run a complete Stage 8 campaign, preserve Stage 9 native logs, and carry out Stage 5–6 independent optical/stats verification. The original research blocker remains [issue #42](https://github.com/smshagor-dev/CyberPhotonics-SPR/issues/42).
