# Physical Evidence Qualification and Registry

CyberPhotonics-SPR separates **software readiness** from **physical claim readiness**. The evidence registry is the controlled bridge between completed real-world work and the `full` system-readiness gate.

The registry does not decide whether an experiment is scientifically good. It verifies that required provenance artifacts exist, their hashes are internally consistent, and evidence is not relabeled across classes without the expected source contract.

## Evidence classes

The qualification registry accepts only the physical/deployment classes:

- `comsol_physics`
- `experimental_sensor`
- `device_benchmark`

Synthetic, surrogate, replay, reproducibility, and release artifacts continue to be handled by the existing reviewer/submission package system.

## 1. Register COMSOL physics evidence

First run a real closed-loop iteration with `--backend comsol`. Then register it:

```bash
python scripts/register_evidence.py \
  --registry outputs/evidence/evidence_registry.json \
  comsol \
  --iteration-dir outputs/closed_loop/iteration_001 \
  --model path/to/validated_model.mph \
  --config path/to/validated_sweep.yaml
```

Qualification requires:

- `iteration_manifest.json` exists;
- manifest `backend` is exactly `comsol`;
- manifest `evidence_class` is exactly `comsol_physics`;
- the current `.mph` SHA-256 matches `comsol_model_sha256` in the iteration manifest;
- the current configuration SHA-256 matches `comsol_config_sha256`;
- simulation results exist;
- `verification.csv` contains the closed-loop decision columns.

A synthetic closed-loop manifest cannot be registered as COMSOL evidence through this path.

## 2. Register experimental sensor evidence

```bash
python scripts/register_evidence.py \
  --registry outputs/evidence/evidence_registry.json \
  experimental \
  --raw-data data/raw/session_001.jsonl \
  --raw-data data/raw/session_001_reference.csv \
  --protocol protocols/session_001.md \
  --calibration calibration/session_001.json \
  --instrument-id SPECTROMETER-001 \
  --acquired-at 2026-08-29T10:30:00+03:00
```

Qualification requires at minimum:

- one or more raw measured-data files;
- an experimental protocol artifact;
- calibration provenance;
- a non-empty instrument identifier;
- a timezone-aware acquisition timestamp.

All supplied artifacts are SHA-256 bound in the registry.

## 3. Register exact-device benchmark evidence

The benchmark JSON must use the runtime benchmark contract generated by the hardware pipeline and contain at least:

```text
iterations
latency_ms_p50
latency_ms_p95
latency_ms_p99
throughput_fps
```

Register it together with the exact deployed model and device identity:

```bash
python scripts/register_evidence.py \
  --registry outputs/evidence/evidence_registry.json \
  device \
  --benchmark outputs/hardware/benchmark.json \
  --model models/edge_ri_predictor_quantized.tflite \
  --device-name "Raspberry Pi 5 8GB" \
  --os-name "Raspberry Pi OS 64-bit" \
  --runtime "LiteRT" \
  --accelerator "CPU"
```

This class must describe the exact device on which the benchmark was measured. A workstation or CI benchmark must not be relabeled as target-device evidence.

## 4. Validate registry integrity

```bash
python scripts/register_evidence.py \
  --registry outputs/evidence/evidence_registry.json \
  validate
```

By default validation re-hashes every referenced artifact. If any file was changed, removed, or replaced after registration, validation fails.

`--no-file-check` is available only for inspecting registry structure after artifacts have been archived elsewhere; it must not be used as the basis of a fresh physical claim.

## 5. Run the full readiness gate

After all three qualified classes are registered:

```bash
python scripts/check_system_readiness.py \
  --profile full \
  --expected-version 1.0.0rc1 \
  --evidence-registry outputs/evidence/evidence_registry.json \
  --json-out outputs/readiness/full.json \
  --markdown-out outputs/readiness/full.md \
  --strict
```

The full gate may also read reviewer/submission manifests. Evidence classes from all supplied sources are merged, but a supplied registry must itself validate successfully.

## Scientific boundary

`manifest_and_hash_validated` means the software validated provenance structure and artifact identity. It does **not** mean:

- a COMSOL model is physically correct;
- a mesh is converged;
- an experimental protocol is unbiased;
- calibration is traceable to a certified standard;
- a device benchmark generalizes to another device;
- a fabricated sensor achieved a claimed detection limit.

Those are scientific and experimental review questions. The registry exists to prevent missing provenance and accidental evidence-class escalation, not to replace peer review.
